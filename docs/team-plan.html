Four steps. It takes about five minutes to read.

1

Section A, B or C. Each one begins with a coloured band carrying your name. If you print this, the band colour tells you whose pages you are holding.

2

"Your job in one sentence" and "Before you start". They tell you what you are building and what has to exist before you can begin.

3

Every task says what to build, which files are yours, and how you know you have finished. Do not jump ahead.

4
Hand in using the last page of your section.

That page gives the exact file names and folders. If you invent your own file names, the work cannot be combined.

The five rules that keep us from breaking each other's work

  1. One file, one owner. Every file in this plan belongs to exactly one person. If a file is not in your task list, it is not yours.
  2. Never edit someone else's file. Need a change there? Ask the owner. They make it. This one rule prevents almost every merge problem.
  3. Agree before you build. The addresses, data shapes and component names are fixed in Appendix A. If something must change, change the appendix first, then tell the team, then write the code.
  4. One job, one owner, start to finish. You own a whole page or a whole module — its look, its logic and its data calls. Not "all the styling" or "all the buttons".
  5. Never merge your own branch. Someone else merges it. That is the cheapest review you will ever get.
Never send these
  • node_modules — it is thousands of files and rebuilds itself.
  • .env — it holds passwords and keys.
  • The whole project folder — send only the files you own.
  • Photos or screenshots of your code. Send the actual text file.
  • Word documents containing code. Word changes quotation marks and breaks the file.
Always send these
  • Your code as real .jsx, .js or .sql files.
  • Proof it works: screenshots or response output, named the way your hand-in page says.
  • Your NOTES.md, even if you finished everything — write "nothing missing".
  • Your checklist page, filled in and dated.
Why the work happens in this order

Frontend first, then database, then backend. The frontend needs no database because it runs on fake data, so it can start today and the design can be checked early. The database must be finished before the backend, because the backend is the code that writes the SQL — if the tables keep changing underneath it, every query gets written twice. Person C has no database tasks, so during that stage C writes the test script and does the phone-sized screen pass.

The four gates

A gate is a short check that must pass before the next stage starts. If a gate fails, fix it — do not push on.

1 · After frontendAll 15 pages open on fake data, in every state, at 390px and 1440px

4 · After combiningThe full journey works with the fake data switched off
What a "finished" task looks like in this project

Not "it works on my machine". Finished means: it matches the design in design/mockups.html; it shows a loading, an empty, an error and a filled state; it works with a narrow window; you can reach every control with the Tab key; there are no red errors in the browser console; and one other person has looked at it.

A.1 · The four item states

StateWhat it meansWhat the student seesWhat the server allows
OPENReported, nothing claimed yetNormal item page, claim button, edit and delete visible to the ownerClaim, edit, delete, archive
CLAIM_PENDINGOne claim is waiting for a decisionClaim button becomes "claim under review"; edit and delete replaced by "locked"Admin decision only. No new claim, no edit
RETURNEDThe claim was approved and the item went backContact block for the two parties; no claim buttonArchive only
ARCHIVEDA flag, not a state. The item keeps its status but disappears from public lists404 if a public visitor opens the link; visible to admin with a Restore buttonRestore only

Why archived is a flag and not a fourth status: an item can be returned and archived at the same time. If both lived in one column you would have to pick one and lose the other. Two columns, two questions, no conflict.

A.2 · The three claim states

StateWho moves it thereNotes
PENDINGThe student, by submitting proofSets the item to CLAIM_PENDING. Only one may exist per item.
APPROVEDThe adminSets the item to RETURNED and unlocks contact details for both parties. One transaction.
REJECTEDThe admin, with a written reasonReturns the item to OPEN. The same student can never claim that item again.

A.7 · Words we use the same way

Endpoint
One address on the server that does one job, for example /api/items.
Middleware
Code that runs before the main job — a door check, for example "is this person logged in".
Token
A long string proving you logged in, stored in the browser and sent with each request.
Hash
A one-way scramble of a password. You can check a password against it, but never turn it back into text.
Seed
Filler rows inserted so the screens have something to show.
Mock / fake data
Made-up data served by the frontend itself, before the real server exists.
Index
A lookup list the database keeps so it can find rows without reading every one.
Transaction
Several database writes that either all succeed or all undo. No half-finished states.
Partial index
An index that only covers rows matching a condition — used here for "only one PENDING claim per item".
Rollback
Undoing a transaction because one part of it failed.
